Structure, shared interfaces, and imports

The canonical implementation is organized by mathematical responsibility. Worked examples live under Examples/; their illustrative data is not part of the reusable theory. Existing flat imports remain forwarding modules.

Entry points and dependency direction

  • Theory.agda publicly exports reusable financial theory.
  • Broker2.agda exports successive versions of one margin engine, with a speaker guide.
  • Broker.agda exports the eight generic broker stages with qualified names.
  • Examples.agda imports all worked applications with qualified names.
  • ../Financial.agda preserves the original public API and qualified examples, and checks both new entry points.

For focused use, import the canonical module directly:

open import Cubical.HITs.CauchyReals.Example.Financial.Margin.Base
import Cubical.HITs.CauchyReals.Example.Financial.Examples.FX.BrokerMargin as Broker

Core/ provides common finite arithmetic, probability, bounds and economic identity. Risk/, Portfolio/, Dynamic/, Instruments/, Margin/, and Settlement/ build the reusable financial statements. Broker/ composes them in a separate, increasingly rich progression of generic margin controllers. These implementations import canonical theory paths; none imports Examples or a legacy forwarding module. Examples may compose related examples. General-purpose example inputs belong in CommonScenarioData, so an FX application does not acquire a dependency on a particular asset portfolio merely to use a uniform probability distribution.

The flagship composed statements are BrokerGuarantees and TradingGuarantees, with motivation and theorem-level contracts in SYSTEM_GUARANTEES.md. The theory entry point exposes the new reusable controls as public qualified namespaces MarginWorkflow, PaymentHistory, and Broker, keeping their status and receipt names separate from the existing scalar controller and settlement API.

One engine evolved for a presentation

Broker2/ contains seven successive engine versions, each importing its predecessor. The recurring operations are quoteCall, receive, and receive-correct. Relationships are proved by client/scenario projection, singleton specialization, rational receipt embedding, zero-MTA equality, identified-receipt accounting, and unchanged-market regression.

The version sequence contains complete engine workflows, including a generic rational factory for exact initial reports, incremental report updates after partial receipts, and a final process result carrying the next state, report, and assessment. It reuses the existing finite-margin, receipt-journal and drift lemmas. The earlier broker progression remains independent. Theory.Broker2 exports qualified version namespaces; no concrete example is imported.

Broker2/Pipeline/ uses Cubical.Experiments.Relation. Implementation/ contains Sources, Valuation, Receipts, Margin, and the standalone Calculation. Properties/ contains the accounting, numeric, safety, refinement, and replay proofs, including a matching Calculation module certifying the result table. Each folder has its own Agda entry point; the pipeline umbrella exposes these two namespaces. The presentation starts with the read-only calculate query: three source tables, derived columns, selection, grouped sums, a maximum over scenarios, and a projected output. The complete margin engine remains available separately. The implementation imports no abstract broker engine or financial safety module. Named field access, finite-key membership, projection, selection, and aggregation are shared relation primitives, rather than per-schema getter wrappers.

Generic broker progression

Broker/README.md gives the stage-by-stage contracts and Broker/REFERENCES.md maps them to primary literature. Stages add cash, arbitrary scenario coverage, client netting, inventory and haircuts, identified receipts, revaluation, minimum transfers, and the final controller. They reuse Core, Risk and Margin without importing worked examples or changing the earlier broker application.

The progression distinguishes exact minimum certificates from sufficient upper reports, a call from a receipt, a minimum-transfer tolerance from full coverage, and proof of an unfulfilled plan from proof of economic deficiency. The journal uses immutable IDs and contributes only newly credited cash. The final controller proves loss bounds for the actual updated ledger, plus equality of the complete ledger/certificate state after replay. It contains no numerical scenarios.

Margin/Base: margin-postCash For every nonnegative real payment, the remaining margin equals the positive part of the original margin less that payment. The rational payment controller specializes it.

The shared example data includes half, quarter, the fair two-state and uniform four-state distributions, halfTail, and three admissible dual measures. The names stress02, stress12, and stress01 identify their nonzero coordinates. Their admissibility depends on the base distribution and tail multiplier; tightness for a particular portfolio is proved by its example. The original Diversification.dualA, dualB, and dualBalanced names remain public aliases.

Scenario certificates and constructive boundaries

For arbitrary states S and a supplied admissibility predicate A:

Coverage A X C b = every admissible state s satisfies X(s) ≤ C(s) + b

MarginCertificate A X C m contains nonnegativity of m, coverage at m, and leastness among nonnegative budgets. It proves m ≤ b ≃ Coverage A X C b when 0 ≤ b.

A BindingScenario A X C m supplies an admissible state with the raw difference X(s) - C(s) = m. Together with coverage at m, this proves the equivalence for all real budgets, preserving the stronger existing joint FX results. Merely knowing stopLoss(X(s), C(s)) = 0 would not suffice: a negative raw difference can leave surplus collateral. The record and equivalence interfaces are universe polymorphic; their univalence paths currently specialize to small state and admissibility types.

Finite maxima are constructive lattice folds. Neither worstCase-exact-at nor margin-exact-at selects a maximizing index for arbitrary Cauchy reals; each consumes explicit evidence. The general finite margin certificate does not require such an index. IsCVaR still requires supplied attainment and a global bound; this refactor does not assume general optimizer existence.

Financial terminology and units

Expression Convention
Scenario loss X Positive is loss, negative is gain, in a common value unit and horizon.
Broker replacement claim Positive is owed to the broker; negative is owed by it. Client netting labels remain explicit.
Signed settlement cashflow Positive is receipt by the broker, negative is a payment owed, in its native currency and date.
stopLoss x c (x - c)⁺; a threshold shortfall generally, and residual exposure when c is eligible collateral.
requiredMargin Least nonnegative uniform domestic cash top-up under the supplied stress policy. It becomes collateral through postCash.
Broker residual exposure Sum of separately clamped client-netting-set claims after collateral. Default/recovery severities turn this into modeled closeout loss.
Tail multiplier κ Reciprocal of tail probability mass, or 1/(1-confidence) as an interpretation; the formal input is κ ≥ 1.
Proportional execution cost Sum of rate times absolute traded amount across all legs. Conventional one-way turnover may be half that total.

These distinctions matter when composing portfolio risk, collateral and settlement models. REFERENCES.md gives their methodological sources and the numerical conventions used in the examples.
